# ADR-001 — DDD + Microservices Architecture

**Date:** 2026-05-18  
**Status:** Accepted  
**Deciders:** Core team

---

## Context

Pakistan CRM OS needs to serve as an execution platform, not just a data store. The system must enforce business rules (follow-up deadlines, payment collection, escalation ladders) across multiple domains that have very different lifecycles and scaling needs. A monolith would make these domains entangled and hard to evolve independently.

---

## Decision

Adopt **Domain-Driven Design (DDD) with a microservices architecture** across three strict layers:

```
L1 — Core (domain models, business logic, engine implementations)
L2 — Interfaces (adapter contracts: MessagingAdapter, PaymentAdapter, etc.)
L3 — Adapters (country-specific implementations: Pakistan JazzCash, WhatsApp)
```

Six platform-owned engines handle cross-domain concerns: Follow-up, Collections, WhatsApp, Activity Control, Activation, Execution Control Plane. No domain re-implements engine logic.

---

## Consequences

**Positive:**
- Domains evolve independently (Follow-up cadence ≠ Collections cadence ≠ WhatsApp throughput)
- Country isolation is enforced structurally — `core/` cannot import `adapters/pakistan/`
- Each engine can be tested, scaled, and deployed independently
- Adding a new country is a new `adapters/<country>/` directory — zero changes to Core

**Negative / Trade-offs:**
- Higher initial complexity vs. a simple monolith
- More boilerplate (interface contracts, adapter registry)
- Requires disciplined ownership — any domain that bypasses L2 and calls L3 directly breaks isolation

**Mitigation:**
- Import rules enforced via ruff (no direct cross-layer imports)
- Architecture rules documented in `architecture-overview.md` and enforced in code review
