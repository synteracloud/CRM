# ADR-002 — Adapter Pattern for Pakistan Market Isolation

**Date:** 2026-05-18  
**Status:** Accepted  
**Deciders:** Core team

---

## Context

Pakistan has specific payment providers (JazzCash, Easypaisa), specific messaging providers (360dialog, Gupshup, Meta WhatsApp Business), specific phone number formatting (E.164 with PK country code), and specific compliance requirements (PTA, FBR). These must not pollute the core domain logic. If any Pakistan-specific provider changes its API, the change must be contained entirely within the adapter layer.

---

## Decision

All country-specific logic lives exclusively in `adapters/pakistan/`. Core domain logic interacts only with stable interface contracts in `adapters/interfaces/`:

| Interface | Implementations |
|---|---|
| `MessagingAdapter` | `Meta API`, `360dialog`, `Gupshup`, `Twilio` |
| `PaymentAdapter` | `JazzCash`, `Easypaisa` |
| `ComplianceAdapter` | Pakistan compliance hooks |
| `PhoneFormatter` | Pakistan E.164 formatter |
| `LocaleAdapter` | PKR formatting, Urdu locale |

**Enforcement rules:**
- `core/*` → `adapters/interfaces/*` ✓ (allowed)
- `core/*` → `adapters/pakistan/*` ✗ (forbidden — caught by ruff import rules)
- Adapter bootstrap registry (`adapters/pakistan/bootstrap/registry.py`) wires concrete implementations at startup

---

## Consequences

**Positive:**
- Adding Bangladesh, UAE, or any other market = new `adapters/<country>/` directory, zero Core changes
- JazzCash API change only touches `adapters/pakistan/payments/jazzcash.py`
- Core unit tests never need payment provider mocks — they test against `PaymentAdapter` interface
- `JAZZCASH_STUB_MODE=true` default ensures no live payment calls during development (C-009)

**Negative / Trade-offs:**
- Every provider integration requires writing both the interface method and the concrete adapter
- Interface design must be stable — changing a method signature in `PaymentAdapter` requires updating all implementations

**Mitigation:**
- Interfaces are minimal by design — only the methods core actually needs
- `AdapterError` taxonomy centralised in `adapters/interfaces/types.py` so error handling is consistent
