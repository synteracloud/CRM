## 1. Summary

**Frontend-backend validation parity is largely NOT ESTABLISHED** as of 2026-06-22.

- 93% of 75 frontend pages use `DUMMY_MODE` — they render from static JavaScript dummy data, not live API
- Only ~10 pages (13%) are wired to the live backend
- Frontend validation logic for form pages has not been systematically audited against backend validation rules

This document records known parity, known gaps, and the parity standard to be achieved when each page is wired.

---

## 2. Parity Standard

When a frontend page is wired to the backend, it MUST implement validation parity for all required fields:

| Rule Category | Backend enforcement | Frontend parity required |
|---|---|---|
| Required fields | 422 validation_error | Form field is required; submit blocked |
| Enum values | 422 invalid_value | Dropdown limits to valid options |
| Phone format (E.164) | DB UNIQUE constraint | Format hint + normalization |
| Amount ≥ 0 / > 0 | DB CHECK constraint | Min value validation |
| Currency ISO 4217 | DB CHECK constraint | Dropdown: PKR default |
| Date range constraints | Business rule validation | Date picker limits |
| Optimistic concurrency | 409 conflict | Auto-reload prompt on 409 |
| Idempotency-Key | 422 if missing | Auto-generated per write attempt |

## 5. Known Parity Gaps

### Gap V-001: Phone number format validation absent on frontend
- **Severity:** High
- **Affected pages:** Lead form, Contact form, all forms with phone input
- **Backend:** Phone stored as E.164, UNIQUE constraint on (tenant_id, phone_e164)
- **Frontend:** No input mask or E.164 format validation confirmed
- **Risk:** Users can submit malformed phone numbers; backend may accept or reject depending on DB constraint enforcement path

### Gap V-002: Idempotency-Key not auto-generated by frontend
- **Severity:** Medium
- **Backend:** All write requests require `Idempotency-Key` header; 422 if missing
- **Frontend:** No evidence of Idempotency-Key generation in crm-shell.js or app JavaScript
- **Risk:** All form submissions will return 422 when pages are wired to live API unless this is added

### Gap V-003: Optimistic concurrency 409 handling absent
- **Severity:** Medium
- **Backend:** PATCH on leads, contacts, accounts, opportunities, quotes, cases requires current version_no; 409 if stale
- **Frontend:** No 409 conflict handler confirmed in frontend JavaScript
- **Risk:** Silent failure or generic error when concurrent edits occur

### Gap V-004: Pakistani phone format not enforced
- **Severity:** Medium
- **Expected format:** +92 followed by 10 digits
- **Frontend:** No country code picker or format guide found on any phone input field
- **Risk:** Users submit local format (0300XXXXXXX) instead of E.164; fails DB constraint

### Gap V-005: Urdu WhatsApp template validation absent
- **Severity:** Medium (P-017 blocker)
- **Backend:** urdu_approved_by field required for Urdu templates
- **Frontend:** Template builder UI in campaign-builder.html — template type selection IS present (confirmed in FEATURE_SCOPE.md Feature 73: "Campaign builder (WhatsApp blast/email/SMS)" Status=Built). The `urdu_approved_by` field must be set before Urdu templates can be submitted (P-017 blocker remains).

## 6. Validation Parity Protocol

When wiring a new page to the backend:

1. Read VALIDATION_RULES.md §4 for all business rules for this entity
2. Map each backend rule to a frontend validation action
3. Add `Idempotency-Key: crypto.randomUUID()` generation to the API call
4. Add `version_no` extraction from GET response and inclusion on PATCH
5. Handle 409 (optimistic concurrency) with reload prompt
6. Handle 422 with per-field error display (map `error.details[].field` to form field highlight)
7. Handle 401 with redirect to login
8. Handle 403 with "permission denied" message (do not expose scope details)
